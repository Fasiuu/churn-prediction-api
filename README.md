# Churn Prediction API

A production-style REST API that serves a customer churn model. It covers input validation, an explanation with every prediction, batch scoring, Prometheus metrics, structured logs, Docker, and a CI pipeline that builds and smoke-tests the container.

The model comes from my [telco churn analysis](https://github.com/f451h/telco-churn-prediction). This repo is about the part that comes after the notebook: **getting a model into a service other systems can call.**

## Endpoints

| Method | Path | What it does |
|---|---|---|
| `GET` | `/health` | liveness check, used by the Docker healthcheck |
| `GET` | `/model/info` | model version, training date, threshold and hold-out metrics |
| `POST` | `/predict` | churn probability, yes/no decision, risk band and the top 3 factors for one customer |
| `POST` | `/predict/batch` | up to 1,000 customers per request |
| `GET` | `/metrics` | Prometheus metrics: request counts, latency histogram, predictions per risk band |
| `GET` | `/docs` | interactive Swagger UI (generated by FastAPI) |

## Example

```bash
curl -X POST localhost:8000/predict -H "Content-Type: application/json" -d '{
  "gender": "Female", "SeniorCitizen": 0, "Partner": "No", "Dependents": "No", "tenure": 3,
  "PhoneService": "Yes", "MultipleLines": "No", "InternetService": "Fiber optic",
  "OnlineSecurity": "No", "OnlineBackup": "No", "DeviceProtection": "No", "TechSupport": "No",
  "StreamingTV": "Yes", "StreamingMovies": "No", "Contract": "Month-to-month",
  "PaperlessBilling": "Yes", "PaymentMethod": "Electronic check",
  "MonthlyCharges": 89.5, "TotalCharges": 265.3}'
```

```json
{

  "will_churn": true,

}
```

## Design decisions

- **Feature engineering lives inside the saved pipeline.** It's a custom scikit-learn transformer in `app/features.py`, so the API sends raw customer fields and can never apply different transformations than training did.
- **Strict validation with Pydantic.**
  - Every categorical field only accepts the values the model was trained on.
  - Numbers have sensible ranges.
  - Contradictory inputs are rejected with a clear `422` instead of returning a silent garbage prediction. For example, `InternetService: "No"` combined with `OnlineSecurity: "Yes"` is refused.
- **Explanations are exact, not approximated.** For logistic regression, each feature's contribution is its scaled value times its coefficient, so the top factors are cheap to compute and fully faithful to the model.
- **A tuned decision threshold.** `will_churn` uses the F1-optimal threshold (0.587) chosen on out-of-fold predictions, not 0.5. It's stored with the model in `metadata.json`.
- **The model is trained inside the Docker image.** That way the pickled pipeline always matches the scikit-learn version installed in the container, which avoids a classic version-mismatch bug.
- **Observability:**
  - every response carries an `x-request-id` header
  - each request is logged as one JSON line
  - latency and prediction counts are exposed for Prometheus

## Model performance (hold-out set, 1,409 customers)

| Metric | Value |
|---|---|
| ROC-AUC | 0.845 |
| PR-AUC | 0.653 |
| Recall (churners caught) | 73% |
| Precision | 55% |
| F1 | 0.63 |

## Latency

Measured in-process with FastAPI's test client on a 2-vCPU machine, after warm-up:

| Request | p50 | p95 |
|---|---|---|
| `/predict` (1 customer) | 22 ms | 32 ms |
| `/predict/batch` (1,000 customers) | 76 ms total | |

Batching is about 300x cheaper per customer, so bulk scoring jobs should use `/predict/batch`.

## Run it

**With Docker**
```bash
docker compose up --build
# open http://localhost:8000/docs
```

**Locally**
```bash
pip install -r requirements-dev.txt
python train.py          # trains and saves models/churn_pipeline.joblib + metadata.json
uvicorn app.main:app --reload
```

## Tests and CI

```bash
pytest -q     # 11 tests
ruff check .
```

The tests check:
- valid and invalid requests (bad categories, missing fields, contradictory inputs)
- batch limits and the metrics endpoint
- that a brand-new month-to-month customer scores riskier than a loyal two-year customer
- that API output matches the saved pipeline exactly on real rows

GitHub Actions (`.github/workflows/ci.yml`) runs lint and tests on every push, then builds the Docker image and smoke-tests the running container with real `curl` requests.

## Project structure

```
app/features.py     feature engineering as a scikit-learn transformer
app/schemas.py      request/response models and validation rules
app/model.py        model loading, predictions and explanations
app/main.py         FastAPI app, middleware, metrics
train.py            trains the pipeline, picks the threshold, writes metadata
tests/              API tests (the model is trained automatically if missing)
Dockerfile          slim image, non-root user, healthcheck
```
